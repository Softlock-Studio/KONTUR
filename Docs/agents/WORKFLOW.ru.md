# Агентный воркфлоу KONTUR — руководство для команды

Как устроена работа с ИИ-агентами в этом репозитории и почему именно так.
Канонические правила для агентов — в `AGENTS.md` (по-английски: небольшие модели
следуют англоязычным инструкциям заметно лучше, и токенов это стоит примерно вдвое
меньше). Этот файл — для людей.

## Идея
Большинство агентов у нас будут работать на моделях с контекстом < 100k токенов.
Главный расход контекста — не длина промпта, а **исследование репозитория**:
модель, которая сама ищет нужные файлы, сжигает половину окна до первой строчки
кода. Поэтому всё построено по принципу «маленькое постоянное ядро + подробности
по запросу»:

- `AGENTS.md` (и `CLAUDE.md`, который его подключает) — всегда в контексте,
  поэтому предельно короткие: правила, конвенции, ссылки. **Не раздувать!**
  Каждая добавленная строка — налог на каждый запуск каждого агента.
- `Docs/agents/map.md` — карта кодовой базы. Агент читает её вместо блуждания
  по папкам. **Добавили/перенесли систему — обновите карту в том же PR.**
- `Docs/agents/systems/*.md` — короткая справка по каждой системе: контракты,
  что можно, что нельзя. Агент читает только релевантную своей задаче.
- `Docs/agents/gdd/*.md` — выжимки из диздока по системам, только факты и
  цифры. Первоисточник — гуглдок гейм-дизайнера (ссылка в `gdd/README.md`);
  выжимки — это кэш: изменился диздок → обновите выжимку в том же PR, что и код.

## Как ставить задачу агенту
Заполните бриф по шаблону `Docs/agents/task-brief-template.md`: цель, какие
файлы в скоупе, какие интерфейсы не ломать, что вне скоупа, критерии готовности.
Это самый сильный рычаг качества — сильнее любого промпт-инжиниринга.
В Claude Code можно попросить сабагента `scout` составить бриф автоматически.

## Скиллы (Claude Code, лежат в `.claude/skills/`, общие для всех)
- `compile-check` — быстрая проверка компиляции через сгенерированный csproj.
- `unity-tests` — тесты в batch-режиме Unity (медленно, перед PR). Требует
  `UNITY_EDITOR_PATH` в `.claude/settings.local.json` — см. `Docs/agents/setup.md`.
- `new-system` — каркас новой системы: папка, неймспейс, интерфейсы, конфиг,
  обновление доков.
- `scene-edit` — изменения сцен/префабов через editor-скрипт, который человек
  запускает в Unity. Агенты **никогда** не правят YAML сцен руками.

## Железные правила Unity (за этим следит и сабагент `unity-reviewer`)
1. `.meta`-файлы двигаются/переименовываются вместе с ассетами. Перед коммитом:
   `pwsh Tools/check-metas.ps1`.
2. Сцены/префабы/`.asset` руками не редактируются — только editor-скрипты
   или шаги для человека в handoff.
3. Переименование `[SerializeField]`-поля — только с `[FormerlySerializedAs]`.
4. `ProjectSettings/` и `Packages/manifest.json` агент не трогает без явного
   задания.

## Конец задачи = handoff
Каждая агентская задача заканчивается блоком: что изменилось, что человеку нужно
сделать руками в Unity (создать ассет, привязать ссылки в сцене, запустить
editor-тул, открыть Unity для генерации `.meta`), какие проверки прогнаны.
Не принимайте PR без этого блока.

## Первичная настройка машины
`Docs/agents/setup.md` — 5 минут: .NET SDK, генерация csproj через IDE, путь к
Unity в `.claude/settings.local.json` (в гит не коммитится).
